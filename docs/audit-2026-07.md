## Batch B1 · Docker image: /data volume unwritable by nonroot (issue #26, wave 1) — **MERGED**

### `Dockerfile.release:8` — Container image declares VOLUME /data on a distroless nonroot image that contains no /data directory, so the default database path is unwritable by uid 65532

**HIGH** · category `correctness` · lenses: deps-config-supply

Both Dockerfile.release (the published ghcr.io/bcrisp4/bfeed image) and Dockerfile set BFEED_DATABASE_PATH=/data/bfeed.db and VOLUME ["/data"], but gcr.io/distroless/static:nonroot has no /data directory and no RUN/COPY step creates one. On `docker run` the engine creates the missing mountpoint as root:root 0755 and a fresh anonymous volume inherits that ownership, so the process (USER nonroot:nonroot, uid 65532) cannot create bfeed.db — `docker run -e BFEED_BASE_URL=... ghcr.io/bcrisp4/bfeed` exits immediately with an SQLite open error on Linux. The README quick-start bind mount (`-v "$PWD/data:/data"`, README.md:63) hits the same wall on Linux when docker auto-creates ./data as root. Distroless has no shell, so users cannot even chown from inside the container.

**Suggested fix:** Create /data owned by nonroot in the image, e.g. in the build stage `RUN mkdir -p /out-data` then `COPY --from=build --chown=nonroot:nonroot /out-data /data` (and the same via a tiny stage or `COPY --chown` in Dockerfile.release), before the VOLUME declaration.



## Batch B2 · Test fidelity: MemStore drift, EXPLAIN guard, coverage gaps (issue #27, wave 1)

### `internal/web/handlers.go:272` — The documented mark-read-on-open invariant of GET /entries/{id} is not asserted by any test

**MEDIUM** · category `test-coverage` · lenses: test-quality

CLAUDE.md calls this load-bearing (reader mutations are designed around it: mark-unread/delete redirect instead of re-rendering precisely because opening marks read). The entry-detail tests (TestEntryDetailFallsBackToSummaryWhenContentEmpty, TestEntryDetailPrefersContentOverSummary, TestReaderRendersActions) only check rendered HTML; none re-fetches the entry from the store to assert Status became read. Deleting the MarkRead call in h.entry leaves the entire suite green while unread counts, the unread list, and history all silently break.

**Suggested fix:** In an entry-detail test, after GET /entries/{id} assert store.GetEntry(...).Status == core.StatusRead and ReadAt != nil.

### `Makefile:52` — sqlc drift check uses `git diff --exit-code`, which cannot detect newly generated (untracked) files

**LOW** · category `test-quality` · lenses: deps-config-supply

Both `make sqlc-check` and the CI sqlc-sync job (.github/workflows/ci.yml:97-99) verify generated-code freshness with `git diff --exit-code internal/store/sqlite/sqlc`, but `git diff` only reports changes to tracked files. If `sqlc generate` emits a brand-new file (a new queries/*.sql file produces a new *.sql.go, or an sqlc version bump adds a file), the check passes even though the generated file was never committed; the gap only surfaces later if/when other code references the missing symbols.

**Suggested fix:** Also fail on untracked output, e.g. `sqlc generate && git diff --exit-code internal/store/sqlite/sqlc && test -z "$(git status --porcelain internal/store/sqlite/sqlc)"` (or `git add -N internal/store/sqlite/sqlc && git diff --exit-code ...`).

### `internal/core/coretest/memstore.go:168` — MemStore.UpsertEntries silently drops the hash-changed in-place update path that the real store implements

**LOW** · category `test-quality` · lenses: reuse-duplication, invariants, test-quality

The real store (internal/store/sqlite/entries.go:66-82) updates an existing (feed_id, guid) entry's title/author/content/summary/published_at/url when the content hash differs ('re-fetched entries upsert by content hash' is a documented invariant in CLAUDE.md). MemStore.UpsertEntries treats any existing GUID as a plain skip, never comparing Hash or updating. Any core/web test of the poll pipeline's in-place-edit behavior written against the fake passes (or can't be written) while the real semantics differ — exactly the 'fake that lies' failure mode CLAUDE.md's own testing conventions warn about ('keep it in sync when store query semantics change, or tests pass against a fake that lies').

**Suggested fix:** In the dup branch, mirror sqlite: if existing.Hash != e.Hash, overwrite Title/Author/Content/Summary/PublishedAt/URL/Hash on the stored entry (and leave Status/Starred/ReadAt untouched).

**Related:** internal/core/coretest/memstore.go:183 MemStore.UpsertEntries silently drops re-fetched entries whose content hash changed, where the real store updates them in place

### `internal/core/coretest/memstore.go:73` — MemStore.ListFeeds returns map-iteration order while the real ListFeeds is ORDER BY title COLLATE NOCASE ASC

**LOW** · category `test-quality` · lenses: reuse-duplication, test-quality

queries/feeds.sql:12 orders the feed list alphabetically (`SELECT * FROM feeds WHERE user_id = ? ORDER BY title COLLATE NOCASE ASC`); MemStore.ListFeeds iterates a Go map, so order is random per run. ListCategories in the same fake deliberately mirrors its NOCASE sort, and ListDueFeeds carries an explicit 'Order is unspecified in this test double' comment — ListFeeds has neither the sort nor the disclaimer. Web tests that render the feeds page (which ranges ListFeeds output into group rows) get nondeterministic row order, so any future assertion on feed ordering will flake or be impossible to write against the fake.

**Suggested fix:** sort.Slice(out, func(i, j int) bool { return strings.ToLower(out[i].Title) < strings.ToLower(out[j].Title) }) — same as the fake's ListCategories.

### `internal/core/coretest/memstore.go:158` — MemStore.DeleteFeed does not cascade tombstones, diverging from the documented feed-delete invariant

**LOW** · category `test-quality` · lenses: invariants

The tombstone invariant states 'Deleting a whole feed cascades its entries AND tombstones away', implemented in sqlite via tombstones.feed_id ON DELETE CASCADE (0001_init.sql:55). MemStore.DeleteFeed deletes the feed's entries and nextExtract state but leaves s.tombstones entries for that feed_id in place. Because MemStore's nextID counter never reuses IDs the stale tombstones can't currently match a re-subscribe, but the fake diverges from the invariant it is supposed to mirror — a future test asserting tombstone cascade (or any ID-reuse change) would pass/fail against lying state.

**Suggested fix:** In DeleteFeed, also delete every s.tombstones key whose feed component equals id (mirror the FK cascade).

### `internal/core/coretest/memstore.go:267` — MemStore.ListEntries lacks the real store's limit>200 clamp

**LOW** · category `test-quality` · lenses: test-quality

store/sqlite ListEntries (entries.go:179) resets any limit <= 0 OR > 200 to 50; MemStore only handles limit <= 0. A caller passing Limit: 500 receives up to 500 rows (and a cursor keyed at position 500) in tests but 50 rows in production, so a handler relying on a large one-shot page would pass its tests and paginate differently live.

**Suggested fix:** Match the real predicate: if limit <= 0 || limit > 200 { limit = 50 }.

### `internal/core/coretest/memstore.go:132` — MemStore.UpdateFeed returns ErrNotFound for a missing feed and ignores user scoping; the real UpdateFeed is an unchecked :exec that silently no-ops

**LOW** · category `test-quality` · lenses: test-quality

queries/feeds.sql UpdateFeed is `-- name: UpdateFeed :exec ... WHERE id = ? AND user_id = ?` and feeds.go:103 never inspects rows-affected, so updating a deleted feed (the poll-racing-a-delete case: PollFeed's recordSuccess/recordError calls UpdateFeed after the user deletes the feed mid-poll) is a silent success in production. Under MemStore it returns ErrNotFound, so PollFeed would propagate an error the real system never produces — a test of that race would encode the wrong contract. Mem also skips the user_id check the SQL enforces.

**Suggested fix:** Return nil when the feed is absent (or when UserID mismatches), mirroring the unchecked UPDATE; keep the field-subset copy as-is.

### `internal/store/sqlite/fts_test.go:74` — FTS5 external-content sync across feed-delete FK cascade is untested; only direct DeleteEntry is covered

**LOW** · category `test-quality` · lenses: probe:fts-external-content-sync-integrity

The FTS index depends on entries_ad (AFTER DELETE trigger, migrations/0004_fts.sql:16) firing for every entries deletion. Entries are deleted via two paths: Store.DeleteEntry (plain DELETE) and Store.DeleteFeed via feed_id ON DELETE CASCADE (migrations/0001_init.sql:35). Empirical verification (throwaway test using the repo's Open() DSN, recursive_triggers=0, modernc.org/sqlite) confirms the cascade DOES fire entries_ad today: after DeleteFeed the FTS index has zero docs for the dead entries, 'integrity-check' passes, and a new insert reusing the freed rowid (entries.id is a non-AUTOINCREMENT rowid alias, so reuse happens immediately) produces no false Search() hits. However fts_test.go only tests the direct-DeleteEntry path (TestFTSInsertStatusDeleteSync lines 74-80). If DeleteFeed's deletion strategy ever changes (e.g. batched hand-written deletes in a path that drops/recreates triggers, or a bulk cleanup that bypasses the entries table's triggers), orphaned FTS docs would silently accumulate and — because rowids are reused — Search() could return a wrong live entry for a dead entry's terms; no test would catch it.

**Suggested fix:** Add a test that inserts entries, calls Store.DeleteFeed, and asserts entries_fts MATCH returns nothing plus INSERT INTO entries_fts(entries_fts) VALUES('integrity-check') succeeds; optionally re-insert to exercise rowid reuse. (Note for orchestrator: the round-2 probe hypothesis — that PRAGMA recursive_triggers=OFF suppresses AFTER DELETE triggers on FK CASCADE deletes, orphaning the FTS index — was empirically REFUTED against the exact schema/pragmas/driver; SQLite's recursive_triggers pragma does not affect FOREIGN KEY action trigger firing. All entries.title/content/summary mutations go through plain INSERT/UPDATE/DELETE covered by the entries_ai/entries_au/entries_ad trio, no INSERT OR REPLACE exists, and migration 0004's rebuild backfill is already tested by TestFTSBackfillsPreexistingRows. No actual desync exists in the current code.)

### `internal/web/handlers.go:615` — Feed deletion is completely untested above the store layer: neither POST /feeds/{id}/delete nor FeedService.Delete has any test

**LOW** · category `test-coverage` · lenses: test-quality

The destructive user flow that removes a feed and cascades away all its entries and tombstones has zero coverage in internal/web and internal/core (grep for DeleteFeed / feeds/{id}/delete across *_test.go matches only store/sqlite/feeds_test.go). A regression in the route pattern, parseID handling, error mapping, or the handler wiring (e.g. wiring Delete to the wrong service) would pass the whole suite. The htmx side (row removal on 200) is likewise unasserted.

**Suggested fix:** Add a web test: seed feed+entries in MemStore, POST /feeds/{id}/delete, assert 200 and that GetFeed/ListEntries show the feed and its entries gone; add a 404/error-path case.

### `internal/web/handlers.go:134` — Cursor pagination ('load more') is untested at the web layer: cursor decoding and the HX-Request fragment branch of renderList have no test

**LOW** · category `test-coverage` · lenses: test-quality

No web test passes ?cursor= (grep for cursor/load more across internal/web/*_test.go returns nothing). The untested logic includes core.DecodeCursor of an attacker-controllable query param, the HX-Request==true && cursor!="" branch that renders the bare entrylist fragment instead of the layout, and NextCursor emission when a 51st row exists. A regression here (e.g. fragment branch rendering the full layout, or a malformed cursor 500ing) ships unnoticed; MemStore does honor Order/Cursor so the test is fully writable today.

**Suggested fix:** Seed 51+ entries, GET / and assert a NextCursor link renders; then GET /?cursor=<value> with HX-Request: true and assert only rows (no <html>/layout) plus correct next page; include a malformed-cursor case.

### `internal/web/handlers.go:114` — Untested web handlers: GET /starred, GET /categories/none, POST /categories/{id}/rename, and the non-reader POST /entries/{id}/delete path

**LOW** · category `test-coverage` · lenses: test-quality

Enumerating routes in web.go against all internal/web/*_test.go: h.starred (handlers.go:114) is never requested (only the Starred filter's fragment rendering is touched indirectly); h.uncategorisedEntries (handlers.go:802) has no test (/categories/none); h.renameCategory (handlers.go:814) has no web test (core covers only the Rename conflict); h.deleteEntry's list-view branch (handlers.go:727, plain 200 without from=reader) is untested — feedback_test.go:143 only covers the reader branch. Each is a swappable route whose breakage the suite cannot detect.

**Suggested fix:** Add one request-level test per route: seed state in MemStore, issue the request, assert status/body and resulting store state.



## Batch B3 · Background-execution safety (panic recovery, shutdown, exit codes) (issue #28, wave 1)

### `internal/core/poller.go:46` — No panic recovery in Poller/Scraper worker goroutines or web background goroutines — one panic on untrusted content kills the process and can crash-loop

**MEDIUM** · category `error-handling` · lenses: concurrency, parse-extract

The Poller worker loop (poller.go:43-50), Scraper worker loop (scraper.go:53-60), and the web background subscribe/refresh goroutines (handlers.go:365-372, 522-529) run with no deferred recover(). net/http only recovers panics in request handlers; a panic in any of these goroutines terminates the entire process. The pipeline in these goroutines processes untrusted input end-to-end (gofeed parse of attacker-controlled feed XML, readability extraction of arbitrary article HTML, sanitizer) — a panic-triggering input in any dependency is a remote DoS. Worse, the offending feed/entry remains due in the DB (next_check_at/next_extract_at unchanged because the poll never completed), so on restart the poller immediately re-dispatches the same input: a persistent crash loop that survives restarts and can only be fixed by hand-editing the DB.

**Suggested fix:** Wrap each job (and each background goroutine body) in a func with `defer func(){ if r := recover(); r != nil { log + record feed/entry error } }()` so one bad input degrades to an error row instead of killing the server.

**Related:** internal/core/scraper.go:56 No panic recovery in background worker goroutines processing untrusted HTML/XML — one pathological page crashes the whole daemon

### `cmd/bfeed/serve.go:113` — serve exits with code 0 when ListenAndServe fails (e.g. port already in use)

**LOW** · category `error-handling` · lenses: concurrency

When ListenAndServe returns a non-ErrServerClosed error (bind failure, port conflict), the goroutine logs it and calls stop(), which cancels ctx; runServe then proceeds through the normal graceful-shutdown path and unconditionally hits `return 0` (line 134), and main.go:23 does os.Exit(runServe()). A server that never listened reports success. systemd Restart=on-failure or a container restart policy keyed on exit code will not restart it, and scripts/CI see success while the app is down.

**Suggested fix:** Record the server error (e.g. send it on a channel or set an atomic flag in the goroutine) and return 1 from runServe when it is set.

### `cmd/bfeed/serve.go:124` — Graceful shutdown does not wait for web background subscribe/refresh goroutines; DB is closed and process exits underneath in-flight writes

**LOW** · category `lifecycle` · lenses: concurrency

Shutdown waits for pollerDone and scraperDone only. The background goroutines spawned by the subscribe and refresh handlers (handlers.go:365, 522) run on context.Background() with a 60s timeout and are tracked only in the web-layer inflightSet, which serve.go cannot see. On SIGTERM, runServe returns after the two waits, the deferred db.Close() (line 43) runs, and main os.Exit()s — while a ResolveAndIngest/Refresh may be mid-UpsertEntries/UpdateFeed. The write fails against the closed pool or the goroutine is killed at exit; the user's subscribe/refresh is silently lost (SQLite WAL keeps the file itself consistent). A subscribe interrupted this way also feeds directly into the one-shot-discovery problem (finding above).

**Suggested fix:** Track the background feed-op goroutines in a sync.WaitGroup owned by the Handler (exposed as e.g. Handler.Drain()) and wait on it in serve.go between srv.Shutdown and db.Close, or derive their contexts from the app ctx with WithoutCancel semantics plus an explicit drain.



## Batch B4 · Feeds that silently never ingest (issue #29, wave 2)

### `internal/parse/parse.go:41` — Items with no parseable date get zero-time PublishedAt, stored as year-1 and sunk to the permanent bottom of every entry list

**MEDIUM** · category `correctness` · lenses: parse-extract, data-integrity

When gofeed cannot parse a date (PublishedParsed and UpdatedParsed both nil — legal RSS without pubDate, or a nonstandard date format), pub stays the zero time.Time. The store persists it via toUnix (store.go:23), giving published_at = -62135596800. All list views and keyset pagination order by published_at DESC, so every new entry from such a feed lands at the absolute end of the list — effectively invisible to the user — and the web layer renders humanizeSince/RFC3339 of year 0001 (nonsense like a huge "ago" value and datetime="0001-01-01T00:00:00Z", handlers.go:948-950). The scheduling code explicitly compensates (WeeklyEntryCount falls back to created_at when published_at is not > 0), showing the dateless case is known, but the parse/display path has no equivalent fallback.

**Suggested fix:** Fall back to the ingest time for undated items (e.g. leave PublishedAt zero in ParsedEntry but have ingest substitute clk.Now()/CreatedAt when pe.PublishedAt.IsZero()), so first-seen ordering matches other feed readers.

### `internal/parse/parse.go:28` — Feed charset from HTTP Content-Type is discarded, so non-UTF-8 feeds without an XML encoding declaration (and UTF-8 feeds containing stray cp1252 bytes) hard-fail every poll permanently

**MEDIUM** · category `correctness` · lenses: probe:charset-encoding-end-to-end

The fetcher captures the Content-Type header (internal/fetch/fetch.go:119) but the charset parameter is never parsed or propagated: core.FeedParser.Parse takes only (data []byte, feedURL string) (internal/core/ports.go:39-41) and PollFeed passes resp.Body raw (internal/core/feed.go:217, also feed.go:174,185 in subscribe). gofeed only transcodes when the XML declaration carries an encoding attribute (goxpp CharsetReader via shared.NewReaderLabel); Go's encoding/xml treats absent/UTF-8 declarations as UTF-8 and rejects invalid bytes. Reproduced with the real adapters: a windows-1251 RSS feed with '<?xml version="1.0"?>' (charset conveyed only via HTTP header, per RFC 3023) fails with 'XML syntax error on line 1: invalid UTF-8'; the identical bytes WITH encoding="windows-1251" in the declaration parse correctly. The same rejection hits the common real-world case of a UTF-8 feed with a few pasted windows-1252 smart-quote bytes. Every poll of such a feed calls recordError (feed.go:218-220) forever — the feed can never be ingested and only shows the stalled badge. Related same-root-cause case reported separately: UTF-16 feeds. Not a documented deferral (no mention of encoding/charset in docs/).

**Suggested fix:** Propagate FetchResponse.ContentType into FeedParser.Parse and wrap the body with golang.org/x/net/html/charset.NewReader(bytes.NewReader(data), contentType) before gofeed — it honors HTTP charset, BOM, and content sniffing, and transcodes to valid UTF-8 (x/net is already a direct dependency).

### `internal/core/feed.go:275` — An ingest (UpsertEntries) failure in recordSuccess skips rescheduling entirely, leaving the feed due forever: tick-rate unconditional refetch with no backoff

**LOW** · category `error-handling` · lenses: core-correctness, error-handling

recordSuccess returns early when ingest fails, before CheckedAt/ErrorCount/NextCheckAt/etag/last_modified are persisted. The feed's next_check_at stays in the past, so ListDueFeeds re-dispatches it on every tick (default 1m); and because the fresh ETag/Last-Modified from the 200 were never stored, each retry is a full-body fetch, not a conditional GET. Fetch and parse errors get exponential backoff via recordError, but store-layer failures (disk full, I/O error, DB locked beyond busy_timeout) get a 1-minute hot loop per due feed for as long as the condition lasts. The same shape exists in ScrapeEntry: a SetEntryContent/UpdateExtractState write failure leaves the entry pending with next_extract_at in the past and attempts unincremented, so the Scraper retries it every tick indefinitely.

**Suggested fix:** On ingest failure, still persist a rescheduled NextCheckAt (e.g. via the recordError path with the store error message) so the feed backs off instead of spinning at tick rate.

### `internal/core/feed.go:174` — resolveFeed rejects a valid but empty feed (blank title, zero entries): subscription fails with 'no feed found at URL'

**LOW** · category `correctness` · lenses: core-correctness

The acceptance condition requires pf.Title != "" || len(pf.Entries) > 0. A syntactically valid RSS/Atom feed that is newly created (no items yet) and has an empty/whitespace title parses fine (perr == nil, pf != nil) but fails the condition, falls through to HTML discovery of a non-HTML body, and returns ErrValidation 'no feed found at URL' — the user cannot subscribe to a legitimate feed until it publishes its first entry or sets a title.

**Suggested fix:** Distinguish 'parsed as a feed' from 'parsed with content' — e.g. accept when the response Content-Type is a feed type or when gofeed identified a FeedType, instead of requiring a title or entries.



## Batch B5 · Redirects & final URL (FetchResponse.FinalURL) (issue #30, wave 2)

### `internal/core/scrape.go:86` — Scraped article HTML resolves relative URLs against the pre-redirect entry URL, permanently persisting broken image/link URLs

**MEDIUM** · category `correctness` · lenses: probe:redirect-final-url-lost-across-pipeline

ScrapeEntry fetches e.URL; the fetch client transparently follows up to 5 redirects (fetch.go capRedirects(5)) but FetchResponse carries no final URL (internal/core/ports.go:12-20; fetch.go:117-123 never reads resp.Request.URL). The fetched body is then passed to Extract and Sanitize with the ORIGINAL e.URL as base. readability (extract.go:33, readability.FromReader(..., u)) absolutizes relative img src / a href against that URL, and sanitize's resolveURL/cleanURL (sanitize.go:98, :108) do the same for anything left relative. Failure scenario: entry URL is a feedburner/feedproxy redirector, a tracking redirect, or a domain that 301-migrated — common in real feeds. Article page at final origin example.com uses src="/images/x.png"; it gets resolved to https://feedproxy.google.com/images/x.png (or old-domain equivalent) — 404. The wrong HTML is then persisted via SetEntryContent with extract_state='done' (scrape.go:99), so it is never re-scraped: broken images and links are baked into the DB permanently.

**Suggested fix:** Add FinalURL to core.FetchResponse, set it in fetch.Client.Fetch from resp.Request.URL.String() (Go sets Response.Request to the last request in the redirect chain), and use resp.FinalURL (falling back to e.URL) as the pageURL for Extract and the base for Sanitize in ScrapeEntry.

### `internal/core/feed.go:177` — Feed autodiscovery resolves relative <link rel=alternate> hrefs against the pre-redirect page URL, producing a nonexistent feed URL

**LOW** · category `correctness` · lenses: probe:redirect-final-url-lost-across-pipeline

resolveFeed fetches rawURL (feed.go:167); if the site page was reached via redirect (www→apex, http→https, domain move), resp.Body is the post-redirect page, but Discover is called with the pre-redirect rawURL (feed.go:177 `s.parser.Discover(resp.Body, rawURL)`). parse.Parser.Discover parses that as the resolution base (parse.go:170 `base, _ := url.Parse(pageURL)`; :188 `resolve(base, href)`). Failure scenario: user subscribes to http://old.example.com which 301s to https://blog.example.io/; the page carries <link rel="alternate" type="application/rss+xml" href="/index.xml">; the discovered URL becomes http://old.example.com/index.xml — the second fetch (feed.go:181) fails or returns non-feed content and the subscription is recorded as 'discovered feed unreachable', or worse, subscribes to a wrong-but-existing URL. The same stale base also affects Parse at feed.go:174/:185 and PollFeed feed.go:217, where relative entry <link>s and SiteURL in the feed body (parse.go:32-36 resolve against feedURL) are resolved against the pre-redirect URL.

**Suggested fix:** Thread the fetch's post-redirect FinalURL through resolveFeed: pass it as the base to parser.Discover and parser.Parse instead of rawURL.

### `internal/core/ports.go:12` — Permanent (301/308) redirects never update feed_url: FetchResponse does not expose the final URL, so a moved feed polls the redirect forever and a re-subscribe to the new canonical URL silently creates a duplicate

**LOW** · category `design` · lenses: probe:feed-identity-and-duplicate-subscription

The fetcher follows up to 5 redirects internally (internal/fetch/fetch.go:68,156) but FetchResponse carries only Status/Body/ETag/LastModified — the post-redirect final URL is discarded. PollFeed (feed.go:204) and resolveFeed therefore keep the pre-redirect URL as the feed's identity. When a publisher permanently moves a feed, bfeed pays the extra redirect hop on every poll indefinitely, and if the user later subscribes to the new canonical URL directly, UNIQUE(user_id, feed_url) does not fire (different string) and a full duplicate feed is created. Not listed as a deferral in docs/roadmap.md (no redirect/301 entry).

**Suggested fix:** Add FinalURL to FetchResponse (from resp.Request.URL after the client follows redirects); on a permanent redirect chain, have PollFeed/ResolveAndIngest call SetFeedURL with the final URL (handling ErrConflict the same way as discovery).

### `internal/fetch/fetch.go:91` — Per-host politeness cap is keyed on the pre-redirect host, so redirected fetches don't count against the target host's budget

**LOW** · category `correctness` · lenses: security-ssrf-fetch

The semaphore is acquired once for u.Host of the original request URL, but http.Client then follows up to 5 redirects inside c.http.Do; a fetch of hostA that 301s to hostB consumes a hostA token while actually hitting hostB. N feeds on distinct hosts that all redirect to one CDN/canonical host can concurrently open N connections to that host, exceeding HostConcurrency — the politeness invariant the semaphore exists to enforce. (Also, keys are not normalized: 'Example.com', 'example.com', and 'example.com:80' get separate budgets.)

**Suggested fix:** Acquire/release the per-host token inside the redirect chain (e.g. via CheckRedirect swapping tokens when the host changes), or at minimum lowercase-normalize and strip default ports from the key.



## Batch B6 · Keyset indexes: missing id DESC tiebreak (issue #31, wave 2)

### `internal/store/sqlite/migrations/0001_init.sql:51` — Feed-scoped and starred list pages degrade to a full scan of the user's entry stream because idx_entries_feed_pub and idx_entries_starred lack the trailing id DESC tiebreak

**MEDIUM** · category `efficiency` · lenses: store-correctness, efficiency, invariants, data-integrity

## Batch B7 · rowid reuse + poll/edit races [design call] (issue #32, wave 3)

### `internal/store/sqlite/migrations/0001_init.sql:12` — SQLite rowid reuse lets an in-flight background subscribe/refresh goroutine write the OLD feed's URL, metadata, and entries onto a NEW feed that recycled the deleted feed's id, while silently suppressing the new feed's own resolve

**MEDIUM** · category `concurrency` · lenses: probe:inflight-refresh-vs-concurrent-feed-mutation

feeds.id is `INTEGER PRIMARY KEY` without AUTOINCREMENT, so SQLite reuses max(rowid)+1 after the highest-id row is deleted. The exact flow the UI encourages — subscribe (row pending), realize the URL is wrong, delete the feed, immediately subscribe to the correct URL — hits this: the first subscribe's ResolveAndIngest goroutine (up to 60s: handlers.go:366 `context.WithTimeout(context.Background(), 60*time.Second)`) still holds a *core.Feed with the old ID. DeleteFeed removes the max-id row; the next CreateFeed reuses that id for the new feed. The stale goroutine then (a) `s.store.SetFeedURL(ctx, f.UserID, f.ID, feedURL)` (feed.go:134) rewrites the NEW feed's feed_url to the old subscription's discovered URL, (b) `s.store.UpsertEntries(ctx, f.ID, entries)` (feed.go:242) inserts the old URL's entries into the new feed (FK passes — the id exists again), and (c) `s.store.UpdateFeed(ctx, f)` (feed.go:297) stamps the old feed's title/site_url/etag/last_modified/next_check_at onto the new row. Compounding it, the second subscribe's `h.busy.start(f.ID)` (handlers.go:364) returns false because the stale goroutine still holds the id in the inflightSet, so NO ResolveAndIngest goroutine is ever spawned for the new feed — HTML discovery never runs for it and only the discovery-less Poller PollFeed will ever touch it. Same corruption via startRefresh (handlers.go:518-530): refresh in flight on the max-id feed, delete, re-subscribe, stale recordSuccess lands on the recycled id. The entries table has the same non-AUTOINCREMENT id and an analogous (narrower) window against the Scraper's SetEntryContent.

**Suggested fix:** Declare feeds.id (and entries.id) INTEGER PRIMARY KEY AUTOINCREMENT so deleted ids are never reused, or make the stale-write impossible by guarding poll-side writes (UpdateFeed/SetFeedURL/UpsertEntries WHERE feed_url = <url the poll started from>, or a feeds.generation counter checked on write).

### `internal/core/feed.go:114` — CreateSubscription sets NextCheckAt=now, so the Poller can PollFeed the pending row concurrently with the background ResolveAndIngest and clobber its result

**LOW** · category `concurrency` · lenses: core-correctness, concurrency

The pending row is immediately due (NextCheckAt: now), and the Poller's next tick (default 1m) will dispatch it while the web layer's background ResolveAndIngest is still in flight (the web inflightSet only dedups web-initiated refreshes, not poller dispatches). Both paths end in store.UpdateFeed with independent in-memory Feed snapshots, last-write-wins. Concrete interleaving for a discovery subscription: ResolveAndIngest discovers the real feed URL, SetFeedURLs it, and recordSuccess writes real title/etag/next_check_at; the concurrently dispatched PollFeed (snapshot taken by ListDueFeeds with the raw HTML URL) gets a parse error and its recordError lands last — overwriting title back to the URL fallback, clearing the freshly written etag/last_modified, setting error_count=1 and a spurious 'parse:' last_error, and pushing next_check_at to backoff. The user sees a just-subscribed feed flip to an error row. It self-heals only on the next successful poll minutes later. The documented 'accepted characteristic' (roadmap.md line 61) covers only the Poller re-dispatching its own in-flight batch, not this web-goroutine-vs-poller race on a brand-new row.

**Suggested fix:** Set the pending row's NextCheckAt a short grace period into the future (e.g. now + poll tick or now + the 60s resolve timeout) so the poller only picks it up if the background resolve died; or exclude checked_at IS NULL rows from ListDueFeeds until first resolve.

### `internal/core/feed.go:229` — Entries ingested by a poll racing a full-content enable are inserted with ExtractState from the stale in-memory feed and are never queued for extraction

**LOW** · category `concurrency` · lenses: probe:inflight-refresh-vs-concurrent-feed-mutation

PollFeed/ResolveAndIngest operate on a Feed struct loaded at dispatch time; ingest derives each new entry's extract state from that snapshot (`state := ExtractNone; if f.FetchFullContent { state = ExtractPending }`, feed.go:228-231). If the user enables full-content (EditFeed → SetFullContent) while a poll of that feed is in flight, MarkFeedEntriesPending backfills only entries existing at toggle time; entries the racing poll inserts moments later carry ExtractNone permanently and are silently skipped by the Scraper (ListPendingExtractions only sees pending). The user sees full-content 'on' but those entries never get extracted; the only recovery is toggling the setting off and on again.

**Suggested fix:** Have ingest read the current fetch_full_content from the DB (or compute extract_state in the INSERT via a subquery on feeds), rather than from the poll-time snapshot.

### `internal/core/feed.go:287` — A poll in flight during an EditFeed URL change writes the old URL's ETag/Last-Modified back after SetFeedURL cleared them, re-enabling the spurious-304 hazard the SQL comment guards against

**LOW** · category `concurrency` · lenses: probe:feed-identity-and-duplicate-subscription

SetFeedURL deliberately clears etag/last_modified because they belong to the old URL (queries/feeds.sql:45-48: reusing them against the new URL 'risks a spurious 304 that skips the new feed's content'). But PollFeed operates on a *Feed snapshot loaded before the fetch: if a background Poller tick has the feed in flight (fetch can take seconds) while the user saves a URL edit, recordSuccess's UpdateFeed (feed.go:297; feeds.go:104-119 writes Etag/LastModified/Title/SiteURL) lands after SetFeedURL and restores the old URL's conditional-GET validators (plus old title/site_url) onto the row now pointing at the new URL. The single-writer pool serializes statements, not this read-modify-write sequence; the inflightSet only guards web-initiated refreshes, not the Poller. **Suggested fix:** Make UpdateFeed guard against a concurrent URL change, e.g. include `AND feed_url = ?` (the URL the poll fetched) in the UPDATE, or have recordSuccess re-read the row and skip the metadata write when feed_url no longer matches.

### `internal/store/sqlite/feeds.go:103` — UpdateFeed is a blind full-row write, so an in-flight poll's recordSuccess/recordError resurrects the stale etag/last_modified that SetFeedURL deliberately cleared

**LOW** · category `concurrency` · lenses: store-correctness, data-integrity

UpdateFeed unconditionally rewrites site_url, title, description, etag, last_modified, disabled, next_check_at, ttl_seconds from a core.Feed struct loaded at poll-dispatch time (core/feed.go recordSuccess:297 / recordError:307). SetFeedURL (queries/feeds.sql:44-48) clears etag/last_modified specifically because reusing the old URL's validators against the new URL 'risks a spurious 304 that skips the new feed's content'. But the background Poller (and web background refresh goroutines) run concurrently with EditFeed: if the user edits a feed's URL while a scheduled poll of that feed is in flight, the poll's closing UpdateFeed writes the OLD URL's etag/last_modified (and title/site_url/description/next_check_at) back over the row after SetFeedURL cleared them, exactly undoing the guard. **Suggested fix:** Guard the poll write, e.g. UPDATE ... WHERE id=? AND user_id=? AND feed_url=? (feed_url captured at dispatch) so a mid-poll URL edit makes the stale write a no-op; or re-read the row inside a transaction before writing.

**Related:** internal/core/feed.go:297 Poll completing after a concurrent feed-URL edit writes the old URL's etag/last_modified back, re-creating the spurious-304 hazard SetFeedURL explicitly clears

### `internal/web/handlers.go:456` — editFeed URL change: startRefresh silently no-ops when a refresh of the OLD URL is already in flight, so the new URL is not fetched until the old-URL poll's adaptive next_check_at (up to MaxInterval, 24h+)

**LOW** · category `concurrency` · lenses: probe:inflight-refresh-vs-concurrent-feed-mutation

editFeed calls `h.startRefresh(id)` on URLChanged, but startRefresh bails when `!h.busy.start(id)` (handlers.go:519-521) — exactly the case where a manual refresh of the OLD URL is mid-flight. **Suggested fix:** On URLChanged, also reset the feed's next_check_at to now (so the Poller picks it up promptly even if startRefresh was suppressed), or have startRefresh queue/retry when the id is busy; additionally clear etag/last_modified in SetFeedURL.



## Batch B8 · Feed identity & deduplication [design call] (issue #33, wave 3)

### `internal/core/feed.go:136` — Subscribing to a site URL whose discovered feed is already subscribed leaves a permanent broken duplicate feed row that re-polls the non-feed URL forever, and the informative conflict message is clobbered on the next poll

**LOW** · category `correctness` · lenses: probe:feed-identity-and-duplicate-subscription

### `internal/core/feed.go:104` — No feed-URL normalization beyond TrimSpace: trivially different spellings of the same feed (trailing slash, http vs https, ?utm_source=...) create real duplicate subscriptions with fully duplicated entries

**LOW** · category `design` · lenses: probe:feed-identity-and-duplicate-subscription

CreateSubscription trims whitespace and checks the scheme, then persists the raw string; resolveFeed returns rawURL verbatim when it parses as a feed (feed.go:174-175), with no canonicalization from the feed's self link. Dedupe is solely the exact-string UNIQUE(user_id, feed_url) constraint (migrations/0001_init.sql:27). Subscribing to https://example.com/feed.xml and later to https://example.com/feed.xml?utm_source=rss (or the http:// variant, or a trailing-slash variant) creates two independent feeds that both poll and both ingest every entry, doubling every item in the unified river with no dedupe across feeds (entry uniqueness is per-feed (feed_id, guid), 0001_init.sql:48). ### `internal/parse/parse.go:39` — Derived-GUID fallback collides for GUID-less items sharing link+title (and is delimiter-injectable), collapsing distinct items into one row with per-poll overwrite churn

**LOW** · category `correctness` · lenses: parse-extract, data-integrity

When items lack a GUID, guid = sha256(link + "|" + title). Two failure modes: (1) items with identical link+title — including feeds where items have neither link nor title, all hashing sha256("|") — collide on (feed_id, guid); UpsertEntries inserts the first and treats every subsequent colliding item as an in-place edit (hash differs), so within one poll item N overwrites item N-1 and only one row survives, then every poll re-churns it (data loss of entries plus constant rewrites that reset a full-content feed's content). (2) The "|" join is ambiguous: link="a|b",title="c" and link="a",title="b|c" produce the same GUID, so a feed author (or attacker-controlled feed) can make distinct items merge. EntryHash (line 70) has the same ambiguous concatenation, allowing distinct (title,content,summary) triples to compare equal so a real edit is skipped.

**Suggested fix:** Use a length-prefixed or hash-per-field construction (e.g. sha256(len(link)|link|len(title)|title)) and include a per-item disambiguator (index or content hash) when link+title are both empty/duplicated.

## Batch B10 · Error handling, silent failures & scrape robustness (issue #35, wave 4)

### `internal/core/scrape.go:83` — ScrapeEntry counts 429/5xx responses (ignoring Retry-After) against the 3-attempt cap, terminally failing extractions on temporarily rate-limited hosts

**MEDIUM** · category `error-handling` · lenses: core-correctness

ScrapeEntry treats every non-200 the same as a content failure and never reads resp.RetryAfter (available on FetchResponse, and honoured on the poll path via PollReschedule). Enabling full-content on an existing feed backfills ALL entries to pending (SetFullContent -> MarkFeedEntriesPending), producing a burst of fetches against one host; if the host answers 429 (or has an outage returning 5xx), each entry burns an attempt. With defaults MaxAttempts=3, BaseBackoff=10m, the three attempts span roughly 30 minutes, after which fail() marks the entries ExtractFailed permanently (scrape.go:107-109) — a sustained half-hour rate-limit or outage converts a whole feed's backlog to terminal extraction failures with no automatic re-queue (recovery requires the user toggling full-content off and on).

**Suggested fix:** For 429/503 (and generally 5xx), reschedule using max(backoff, resp.RetryAfter) without incrementing attempts (or with a separate, higher cap), mirroring PollFeed's 429/5xx branch; keep the attempt cap for genuine content failures.

### `internal/core/feed.go:202` — A discovery-based subscription whose initial ResolveAndIngest fails can never recover: PollFeed and Refresh have no discovery fallback

**LOW** · category `correctness` · lenses: core-correctness, concurrency

HTML feed discovery exists only in resolveFeed, which is called solely from ResolveAndIngest (the one-shot background subscribe goroutine, capped at 60s in web/handlers.go:366). If a user subscribes with a site page URL (relying on discovery) and that first resolve fails for any reason — transient network error, slow site exceeding the 60s timeout, or process restart before/during the goroutine — the feed row is left pointing at the HTML page URL. From then on, every scheduled poll (Poller -> PollFeed) and every manual refresh (Refresh -> PollFeed, feed.go:192-198) fetches the HTML page and fails at s.parser.Parse (feed.go:217-219) with a permanent 'parse: gofeed parse: ...' error. There is no code path that ever re-attempts discovery, so the feed is stuck in an error state forever; the only recovery is the user hand-editing the URL or deleting and re-subscribing.

**Suggested fix:** In PollFeed, when parse fails and the response looks like HTML (or the feed has CheckedAt == nil / has never succeeded), fall back to parser.Discover and persist the discovered URL — or route never-successful feeds through ResolveAndIngest instead of PollFeed.

**Related:** internal/core/feed.go:131 Feed resolution/discovery is one-shot with a 60s budget, and its outcome cannot be persisted once that context expires — an HTML-URL subscribe that times out is permanently broken

### `internal/core/feed.go:361` — EditFeed applies edits non-atomically, then the web layer reports the whole save as failed after part of it persisted

**LOW** · category `error-handling` · lenses: error-handling, core-correctness

EditFeed performs four independent writes in sequence (SetFeedUserTitle line 347, SetFeedCategory line 351, SetFullContent line 357, SetFeedURL line 362) with no transaction. A mid-sequence failure leaves earlier writes committed. This is user-triggerable in normal use: edit a feed's title AND change its URL to one that duplicates another subscribed feed -> SetFeedURL returns ErrConflict -> handlers.go renderEditError shows 'A feed with that URL already exists.' (422), implying nothing saved — but the rename, category move, and full-content toggle (which may have re-queued every entry for extraction via MarkFeedEntriesPending) have already persisted. A category change that persisted before a later failure also skips the HX-Refresh path, so the row silently sits in the wrong group until a manual reload.

**Suggested fix:** Validate the URL change first (it is the only step with a realistic conflict) and apply it before the other writes, or run all steps in one store transaction; alternatively report partial success accurately in the edit-error fragment.

**Related:** internal/core/feed.go:347 EditFeed is non-atomic: title/category/full-content writes persist even when a later step fails and the UI reports the whole edit as failed

### `internal/core/feed.go:70` — SetFullContent can enable the flag but silently lose the backfill: MarkFeedEntriesPending failure leaves existing entries permanently unqueued

**LOW** · category `error-handling` · lenses: core-correctness

SetFullContent writes the fetch_full_content flag first, then queues existing entries. If MarkFeedEntriesPending fails after SetFeedFullContent succeeded, the error is returned but the flag stays on: newly ingested entries will be marked pending (ingest checks f.FetchFullContent), but the existing backlog stays extract_state='none' forever — nothing ever reconciles flag-on feeds with unqueued entries. The user sees full-content 'enabled' yet old entries never get extracted; the only fix is toggling off and on again (which they have no reason to know).

**Suggested fix:** Perform both writes in one store transaction (single store method), or roll the flag back when the backfill write fails.

### `internal/core/feed.go:307` — recordError persists the failure using the same context whose cancellation/deadline caused the failure, so the error state is silently lost

**LOW** · category `error-handling` · lenses: error-handling

recordError (and recordSuccess) write the feed's error/reschedule state via s.store.UpdateFeed(ctx, f) with the caller's ctx. When the poll error IS a context deadline/cancellation, the persist is guaranteed to fail too. Concrete case: the background subscribe goroutine (handlers.go:366) uses a 60s timeout; resolveFeed can consume the full budget (two sequential 30s-timeout fetches for HTML discovery, plus per-host semaphore waits in fetch.Client.Fetch). When the deadline expires, ResolveAndIngest -> recordError -> UpdateFeed fails with the expired ctx, the error is only slog-logged, and the designed pending-row-becomes-error-row UX never happens: the user sees a feed row with no error, no CheckedAt, and no indication the subscribe failed until the scheduler's next tick happens to retry and record an error with a live ctx. The same applies to in-flight polls at server shutdown.

**Suggested fix:** Persist the error state with a short fresh context (e.g. context.WithTimeout(context.WithoutCancel(ctx), 5*time.Second)) so recording survives cancellation of the operation that failed.

### `internal/core/scrape.go:107` — Re-enabling full content gives previously terminally-failed entries only a single retry before going terminal again

**Suggested fix:** Have MarkFeedEntriesPending also set extract_attempts = 0 when re-queueing 'failed' entries.

**Related:** internal/store/sqlite/queries/entries.sql:39 Re-enabling full-content does not reset extract_attempts, so previously-failed entries go terminally 'failed' after a single new failure

### `internal/core/scrape.go:84` — Scrape failure detail is discarded: the non-200/non-HTML message drops the actual status and content type, and no failure reason is ever persisted

**LOW** · category `error-handling` · lenses: error-handling

ScrapeEntry collapses two distinct conditions (HTTP status != 200; non-HTML content type) into the fixed string 'non-html or non-200 status', losing resp.Status and resp.ContentType even from the log line. Additionally, fail() only slog-logs the reason; entries carry no error column, so once extract_state reaches terminal 'failed' after MaxAttempts there is no way to see why extraction failed for an entry — the feed-provided summary silently remains and the failure is invisible in the UI and undiagnosable from the DB.

**LOW** · category `error-handling` · lenses: error-handling

entry (line 266-269), toggleEntry (635-638), readerToggleStar (695-698), categoryEntries (794-797), and feedEditForm (413-417) treat any error from Get — including transient DB failures, context cancellation, or I/O errors — as http.NotFound. ## Batch B11 · Security hardening (issue #36, wave 4)

### `internal/web/web.go:54` — No Host-header validation enables DNS-rebinding to read private feed content cross-origin

**MEDIUM** · category `security` · lenses: security-web-misc, invariants

The http.ServeMux patterns carry no host component and nothing validates the request Host against BFEED_BASE_URL. An attacker page at evil.example can lower its DNS TTL, resolve evil.example to the bfeed tailnet IP after initial load, then issue same-origin fetch()s to bfeed. With no Host check the server answers, so the attacker's JS origin can now read full response bodies (feed contents, subscription list, entry text) and drive every mutating endpoint, defeating the browser same-origin protection the no-auth/tailnet model relies on. Host validation is the standard defence and is absent.

**Suggested fix:** Add middleware that rejects (421/403) any request whose Host header is not the expected BaseURL host; this closes DNS-rebinding and complements the CSRF Origin check.

**Related:** internal/web/web.go:93 No Host-header validation enables DNS-rebinding read/write access from any website the tailnet user visits

### `internal/core/reschedule.go:29` — Retry-After is accepted uncapped (and can overflow), letting a hostile feed server park a feed arbitrarily far in the future, bypassing MaxBackoff

**LOW** · category `correctness` · lenses: security-ssrf-fetch

parseRetryAfter (internal/fetch/fetch.go:145-146) converts any numeric Retry-After via strconv.Atoi with no upper bound: a 429/5xx response with 'Retry-After: 315360000' (10 years) flows into PollReschedule, where 'if retryAfter > delay { delay = retryAfter }' overrides the MaxBackoff cap that bounds the exponential path, so feeds.next_check_at is set a decade out and the feed silently never polls again (only a manual refresh recovers it). Additionally, time.Duration(secs)*time.Second overflows int64 for secs > ~9.2e9, producing a garbage (possibly huge positive) duration. The date form is also uncapped (time.Until of a far-future date). Feed servers are untrusted input per the threat model.

**Suggested fix:** Clamp the parsed Retry-After in parseRetryAfter (e.g. min(value, 24h) and reject values that would overflow before multiplying), or clamp retryAfter to cfg.MaxBackoff in PollReschedule.

### `internal/fetch/fetch.go:129` — Bodies larger than MaxBytes are silently truncated at exactly the cap and treated as complete responses

**LOW** · category `correctness` · lenses: security-ssrf-fetch, error-handling

Fetch reads io.LimitReader(resp.Body, c.cfg.MaxBytes) and returns Status 200 with the truncated bytes, with no signal that truncation occurred. Consequences: (1) imgproxy (internal/imgproxy/handler.go:68) serves the truncated bytes of any image >10MB with HTTP 200, Content-Type image/*, and 'Cache-Control: public, max-age=31536000, immutable' — the broken image is then cached by the browser for a year with no recovery path; the truncated write also mismatches no declared Content-Length only because none is set, so the client can't detect it either. (2) ScrapeEntry (internal/core/scrape.go:86) extracts from truncated HTML — an HTML parser accepts a truncated document — so a partial article is sanitised, persisted via SetEntryContent, and marked extract_state='done', permanently replacing the (complete) feed-provided content with a silently cut-off article.

**Suggested fix:** Read MaxBytes+1 and treat len(body) > MaxBytes as an error (return a 'response too large' error, or set a Truncated flag callers must honor); imgproxy and scrape should fail rather than serve/persist truncated data.

### `internal/fetch/fetch.go:68` — fetch.New applies no default Timeout: a zero-value Config produces an HTTP client that can hang forever on a stalled server

**LOW** · category `error-handling` · lenses: security-ssrf-fetch

New() back-fills defaults for HostConcurrency (<=0 -> 3) and MaxBytes (<=0 -> 10MB) but not Timeout, so Config{Timeout: 0} yields http.Client{Timeout: 0} (unbounded). The background Poller/Scraper run on the long-lived serve context with no per-poll deadline, so a server that accepts the connection and never responds would pin a worker slot and its per-host semaphore token indefinitely. Currently latent: cmd/bfeed/serve.go:49 hardcodes 30s, but the constructor's partial-defaulting is a trap for any other construction site (tests, future callers).

**Suggested fix:** In New(), default cfg.Timeout to e.g. 30*time.Second when <= 0, matching the other field defaults.

The guard's explicit blocklist covers CGNAT, 0/8, Class E, 6to4, and NAT64, and netip predicates cover loopback/private/link-local/multicast, but other IETF special-use ranges pass as 'safely public': 198.18.0.0/15 (RFC 2544 benchmarking, deployed as internal address space in some real networks), 192.0.0.0/24 (IETF protocol assignments, incl. ### `internal/fetch/fetch.go:80` — Per-host semaphore map grows without bound, and its keys are attacker-influenced hostnames from untrusted feed content

## Batch B12 · Performance & indexing (issue #37, wave 5)

### `internal/core/feed.go:236` — Every non-304 poll re-sanitises Content and Summary of every entry in the feed before the unchanged-hash check, doing 2×N full HTML parse+render+bluemonday passes even when nothing changed

**LOW** · category `efficiency` · lenses: efficiency

ingest (feed.go:232-241) calls s.san.Sanitize on pe.Content and pe.Summary for all parsed entries; each Sanitize is an html.Parse + tree walk + html.Render + a second bluemonday pass (sanitize.go:34-37). Only afterwards does UpsertEntries compare existing.Hash != e.Hash (entries.go:68) and skip the write — and the hash is computed from the RAW parsed text (parse.go:61 EntryHash), not the sanitised output, so sanitisation could be deferred until an entry is known new/changed with identical results. For feeds whose servers ignore conditional GET (common), every poll of a 50-entry feed burns ~100 redundant sanitise passes; multiplied across all feeds each tick this is the poller's dominant CPU cost in steady state.

**Suggested fix:** Pass raw content+summary into the upsert path (or a pre-check of (feed_id,guid)->hash) and sanitise only entries that are new or hash-changed; the sanitise-before-persist invariant is preserved because sanitisation still precedes the write.

### `internal/imgproxy/handler.go:42` — Image proxy buffers each upstream image fully in memory (up to the 10MB fetch cap) before writing, with no streaming and no Content-Length

**LOW** · category `efficiency` · lenses: efficiency

Opening a scraped article whose page has many images triggers a burst of parallel /img requests, each holding up to a 10MB buffer for the duration of the upstream fetch; peak memory is (#concurrent images × image size) rather than a fixed streaming buffer. **Suggested fix:** Give the image proxy a streaming fetch variant (io.Copy from a limited reader to the ResponseWriter after the content-type check) instead of the buffering core.Fetcher, or set a smaller MaxBytes for image fetches.

### `internal/store/sqlite/entries.go:183` — List and search views read the full entry content column (potentially megabytes of scraped article HTML per row) for 50 rows per page although list rows render only a 280-char summary derived from the first 2048 bytes

**LOW** · category `efficiency` · lenses: efficiency

### `internal/store/sqlite/migrations/0004_fts.sql:10` — FTS index tokenizes raw sanitized HTML, so searches match markup (tag names, attributes, URLs) instead of only visible text

**LOW** · category `design` · lenses: data-integrity

entries_fts indexes entries.content/summary verbatim, and those columns store sanitized HTML (the sanitize-before-persist invariant), not plain text. unicode61 tokenizes tag names, attribute names, class values, and every URL component, so user queries like "https", "img", "blank" (rel=noopener target=_blank), or any word appearing in a link href match essentially every entry, and bm25 ranking is skewed by markup token frequency. After full-content extraction (SetEntryContent) the indexed content is an entire article's HTML, amplifying the noise.

**Suggested fix:** Index a text-only projection (strip tags in the triggers is impractical in pure SQL; instead store a plain-text shadow column populated at ingest/extract time and point the FTS content columns at it), or at minimum document the limitation.

### `internal/store/sqlite/queries/feeds.sql:39` — EntryStatsByFeed is an O(all-entries) GROUP BY with a temp B-tree, executed on nearly every request — including each in-flight feed row's 1500ms self-poll — and serialized on the single-connection pool

**LOW** · category `efficiency` · lenses: efficiency

EXPLAIN on the real schema: 'SEARCH entries USING INDEX idx_entries_user_pub (user_id=?)' + 'USE TEMP B-TREE FOR GROUP BY' (no index leads with (user_id, feed_id)); measured 22ms at 100k entries. Call sites: renderList runs it on EVERY unread page load just to print the header total (handlers.go:167) and on every single-feed page for one feed's two counts (handlers.go:177); listFeeds (handlers.go:306); feedEditForm (:418); renderEditError (:475); and renderFeedRow (:545), which backs GET /feeds/{id}/row — the fragment each refreshing/pending feed row requests every 1500ms (rows_feed.gohtml:3 hx-trigger="every 1500ms"). Subscribe/refresh K feeds at once and you get K×0.67 full-table aggregates per second, all queued behind db.SetMaxOpenConns(1) (db.go:26) together with poll writes and page loads. The unread header needs only COUNT(*) WHERE user_id=? AND status='unread' (covered by idx_entries_user_status_pub, ~0ms), the single-feed header needs a two-count query for one feed_id, and the row poll needs stats for one feed, not all feeds.

**Suggested fix:** Add single-purpose queries: an index-covered unread COUNT for the list header, and a per-feed stats query (WHERE user_id=? AND feed_id=?) for renderFeedRow/feedEditForm; keep the full GROUP BY only for the feeds index page. Optionally add index (user_id, feed_id, status) to kill the temp B-tree there.

### `internal/web/summary.go:71` — summaryText truncates raw HTML at a byte offset, so the 2048-byte cut can land mid-tag or mid-rune, leaking tag fragments/invalid UTF-8 into the blurb or wrongly failing the link-density check

**LOW** · category `correctness` · lenses: web-ui, security-xss

scan[:maxSummaryScan] slices the HTML string at a fixed byte offset with no tag or rune awareness. If the cut lands inside a tag (likely for scraped full-content HTML whose img/a tags carry long absolutized URLs), tagRE (`<[^>]*>`) cannot match the unterminated tag, so its remnant (e.g. `img src="https://long-url...`) survives htmlToText as literal text: it either appears as visible junk at the end of a short blurb, or its URL characters inflate goodPreview's urlChars/len ratio past maxLinkDensity 0.4 and suppress a preview that genuine prose would have earned. If the cut splits a multi-byte UTF-8 sequence, the invalid trailing bytes survive into the preview and render as U+FFFD. Not an XSS (the template re-escapes), purely a data-quality bug on the boundary case.

**Suggested fix:** After slicing, trim back to the last '<' if it begins an unterminated tag (e.g. cut at strings.LastIndexByte(scan, '<') when it has no closing '>' after it) and trim trailing invalid UTF-8 with strings.ToValidUTF8 or by backing up to a rune boundary.

### `internal/config/config.go:112` — Malformed env values are silently replaced by defaults, contradicting the documented 'validated at startup' contract

**LOW** · category `config` · lenses: design-architecture, deps-config-supply

envInt/envFloat/envDur/envBool all swallow parse errors and return the default. A user who sets BFEED_SCHED_MAX_INTERVAL=48 (meaning 48h), BFEED_POLL_TICK=30 (meaning 30s), or BFEED_IMAGE_PROXY=disabled gets the built-in default with no error and no log line, and the process starts as if configured. docs/mvp-design.md §13 states config is 'Validated at startup; sensible defaults', but only BaseURL, worker/host-concurrency, sched min/max, factor, and error-limit are actually validated; PollTick, MaxBackoff, BatchSize, ScrapeWorkers/Tick/Batch/MaxAttempts accept garbage or negative values that are then silently re-normalized deep inside core constructors (NewPoller/NewScraper/NewFeedService/NewScrapeService), so a misconfiguration is undetectable from logs.

### `internal/core/feed.go:76` — FeedService.SetCategory has no production callers and EditFeed reimplements its body inline

### `internal/core/poller.go:17` — Interface-breadth asymmetry between the documented Poller/Scraper and FeedService/ScrapeService pairs

**LOW** · category `design` · lenses: design-architecture

CLAUDE.md and the docs present Scraper/ScrapeService as the exact analogue of Poller/FeedService, but the dependency shapes diverge: Scraper consumes a one-method consumer-owned `pendingLister` (scraper.go:18-20) and ScrapeService a two-method `scrapeStore` (scrape.go:18-22), while Poller demands the full 13-method core.FeedStore of which it calls only ListDueFeeds, and FeedService demands the full core.Store including SearchIndex and SettingStore it never touches. ### `internal/parse/parse.go:56` — Entry titles (and author names) are stored with raw markup/entities and rendered as literal text — Atom type="html" titles display their tags

**LOW** · category `correctness` · lenses: security-xss

Parse copies it.Title and it.Author.Name verbatim; nothing strips tags or decodes HTML entities from these text-only fields anywhere in the pipeline (only Content/Summary pass the sanitizer, feed.go:236-237). Templates auto-escape, so there is no XSS, but the escaping makes any markup visible: an Atom feed with <title type="html">Ben&amp;#39;s &lt;em&gt;post&lt;/em&gt;</title> (gofeed returns the string `Ben&#39;s <em>post</em>`) renders in the list row and reader <h1> as the literal text "Ben&#39;s <em>post</em>". ### `internal/store/sqlite/entries.go:354` — Keyset cursor-key derivation (sortKey) is duplicated verbatim as memSortKey in coretest

**LOW** · category `reuse` · lenses: reuse-duplication

### `internal/store/sqlite/migrations/0001_init.sql:2` — PRAGMA foreign_keys=OFF in migration 0001 is a silent no-op with no matching re-enable — dead now, a latent FK-enforcement kill-switch if any migration ever runs outside a transaction

**LOW** · category `correctness` · lenses: store-correctness

goose runs each migration inside a transaction (no `-- +goose NO TRANSACTION` annotation anywhere), and SQLite's `PRAGMA foreign_keys` is documented as a no-op inside a transaction, so this statement currently does nothing — the CREATE TABLEs run with foreign_keys still ON from the DSN (`_pragma=foreign_keys(ON)` in db.go:20). It is misleading (implies FK checks are relaxed during init) and there is no `PRAGMA foreign_keys=ON` at the end of the migration. Failure scenario: a future schema-rebuild migration adds `-- +goose NO TRANSACTION` (the usual reason to want this pragma); the OFF then actually takes effect on the pool's single connection, which — with SetMaxOpenConns(1) and no ConnMaxLifetime — lives for the whole process, silently disabling all FK enforcement including the ON DELETE CASCADE cleanup that DeleteFeed depends on, leaving orphaned entries/tombstones after every feed delete until restart.

**Suggested fix:** Delete the pragma (it does nothing today); if a future out-of-transaction migration needs it, pair it with an explicit PRAGMA foreign_keys=ON at the end.

### `internal/web/handlers.go:468` — renderEditError duplicates feedEditForm's edit-row construction block
